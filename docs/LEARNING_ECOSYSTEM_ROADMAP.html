Why teachers reteach

Students forget what they practiced too little between lessons — school exams, phones, unclear homework, and zero accountability all work against the studio. The app currently ends at the lesson. This roadmap is about extending it past the door.

Five principles this whole plan is checked against

  1. Every lesson continues after the student goes home. Nothing here is worth building if it doesn't create a reason to open the app between Tuesday and Tuesday.
  2. Homework is actionable, not vague. "Bars 1–8, left hand, tempo 60, 10 minutes" — never "practice piece X."
  3. Motivate, don't pressure. No XP penalties, no shaming streak-breaks, no raw scores shown where they'd read as judgment.
  4. Parents are helpers, not inspectors. Read-only, curated, never a surveillance panel.
  5. Teachers teach more, repeat less. Every feature should remove reteaching time, not add admin time.
CROSS-CUTTING

Architecture foundations

Five designs were drafted in parallel against the live codebase, then adversarially reviewed. Two of them collided — the decisions below are the reconciled result, made once so every phase builds against the same ground truth instead of five slightly different ones. See the review for how each was found.

1. One access model: signed tokens, not accounts

Today only the teacher has a login — protectedProcedure everywhere, one User 1:1 one Teacher, no role concept anywhere in src/server/api/trpc.ts. Giving students and parents a real second-class NextAuth account would mean auditing and role-gating every one of the app's routers (none of them centralize authorization — each hand-rolls its own teacherId scoping), rebuilding proxy.ts into a role-aware router, and standing up account provisioning that doesn't exist even for a second teacher. Call it 3–4× the cost of the alternative, plus a permanent tax on every future procedure.

Instead: a single hashed, opaque access token per student, resolved by a new tRPC middleware — not a session, not a role, just a scoped capability. A bug here can leak at most one student's practice/report data; it can never touch the teacher's login, billing, or any other family's records.

ModelFieldDecision

Updated 2026-07-28: Phase 1 Slice 1B — not Parent Portal — now builds against it first, see Build sequence.

One guardrail neither original design fully committed to: a small in-memory sliding-window throttle on the token-resolution middleware itself. Brute-forcing a 256-bit token is not a realistic threat, but this is the app's first-ever unauthenticated write surface, and volumetric abuse of the lookup path is a distinct, cheap-to-close risk — about twenty lines, shipped on day one, not deferred.

2. One canonical hub per student

Today students/[id]/page.tsx doesn't exist — the students list is a table plus an edit sheet, and the only per-student route is the separate top-level /reports/[studentId]. Three of the five phase designs each assumed a different per-student destination (a /homework query param, a students/[id]/motivation route, a students/[id] route). Building all three literally would scatter "everything about Priya" across five disconnected screens.

Decision: students/[id]/page.tsx is the one new canonical hub — hero, then tabs for Profile, Homework, Motivation, Competitions, with a link out to the existing /reports/[studentId] for the monthly report rather than duplicating it. Every phase below builds a tab on this page, not a new route.

3. Ledgers, not mutable balances

This app already has a rule it just hasn't named: Lesson.rate is frozen at write time, PaymentTransaction is an immutable row against a PaymentMonth, never a single balance field. Every new "score that goes up over time" in this plan — XP, AI usage, notification history — follows the same shape: an append-only table of dated events, with the running total computed live (SUM()/aggregate) rather than cached and drifted. At this app's scale (one teacher, tens of students) that costs nothing and can never go stale.

PHASE 1 · HIGHEST PRIORITY 2 slices

Homework System

Actionable assignments, a five-item daily checklist, a practice timer, and a green/red practice calendar. This is the phase the entire vision depends on — it's also the one most gated by "how does a student interact with the app at all," since today nobody but the teacher has a way in.

Effort: L (not XL) 3 new models 2 new routers Blocks Phase 2 practice-XP, most of Phase 5

Ships in two slices, not one PR

Core Principle #1 and the token-auth question are separable, with very different risk profiles — splitting them means real value lands fast without waiting on the app's first new auth primitive.

model HomeworkLog {                        // one row per (homeworkId, date)
  id, homeworkId, studentId, teacherId
  date          DateTime  // ALWAYS getStartOfDayUTC(raw, teacherTimezone) — never a raw client timestamp
  warmup, leftHand, rightHand, bothHands, performance   Boolean @default(false)
  durationMin   Int @default(0)          // incremented, not overwritten — a student may run the timer twice a day
  loggedBy      HomeworkLogSource @default(TEACHER)     // TEACHER | STUDENT_TOKEN, audit trail
  @@unique([homeworkId, date])
}

model StudentAccessToken { /* shared model — see Architecture Foundations §1 */ }
Deliberate simplificationLATE is computed on read (status ∈ {NOT_STARTED, STARTED} AND dueDate < now), not stored — this app has no cron/background-job infrastructure today, and a stored flag would need one to flip at the due-date instant, plus a way to un-flip it if the teacher extends the date. Revisit only if a "was late at the time" audit trail becomes an actual requirement.

Open risks & product questions (4)
  • Retroactive-edit integrity is enforced structurally (same-day-only writes), because Phase 2's eventual XP ledger needs to trust this data as immutable history — a rule only enforced client-side isn't a rule.
  • Who holds the device? With no email/SMS infra, sharing a link is manual copy-paste. Is the target device the student's own, or a shared family device near the piano? Changes UI tone and whether "revoke on leak" is realistic for dozens of tokens. Needs Soham's call.
  • The timer is a self-report, not telemetry. No anti-cheat, by design (Principle #3) — the UI copy should say so rather than implying it's ground truth.
  • One token per student, not per household, even for siblings sharing a tablet — simpler, safer default; keeps Family (explicitly documented as not an auth graph) out of the auth path entirely.

How this coexists with the existing lesson-score leaderboard

Lesson.score already powers a "Top Students This Month" podium on the dashboard — a teacher's subjective read of lesson quality. XP answers a different question: how consistently is this student showing up and working, over time? They're separate signals, shown as two honest, parallel leaderboards. The only coupling is one-directional: completing a scored lesson adds a small XP bonus. Nothing about the existing query, card, or score field changes.

No penalty branch exists anywhere — a SKIPPED homework earns nothing but loses nothing, per Principle #3. totalXp is never stored, only summed on read, same posture as the existing avgScore computation.

30 levels, six named tiers

Cumulative curve 50 × L × (L+1), precomputed into a static array. Sanity-checked against a moderately engaged student (~150–200 XP/week): Level 5 in ~2 months, Level 10 in ~7–8 months, Level 30 in 5+ years — a multi-year arc for a system meant to span a student's whole time in the studio.

1–5 Sprout: Tiny Pianist → Blossom Player 11–15 Bronze 16–20 Silver 21–25 Gold 26–30 Legend: … → Grand Performer

Badges

Automatic (Perfect Week, Streak 3/7/10/30, 30 Practices, 100 Hours) — checked synchronously the moment a practice day is logged, since there's no cron infrastructure to check them on a schedule. Manual (First Recital, Competition Ready) — awarded by the teacher via a dedicated mutation, because no phase in this plan owns a Recital/Competition event model to trigger them from automatically. That's a real gap, not a shortcut disguised as one.

Mochi's mood — zero new component work

Mochi already accepts a mood prop with three values and already meows on click. Phase 2's entire "pet" mechanic is one function: mood = daysSinceLastPractice === 0 ? "delighted" : ≤2 ? "content" : "sleepy", computed server-side and passed in. No new SVG, no new state model.

Required fix before implementationThe original design wired the XP-on-lesson-attendance hook into lesson.markAttendance as "fire-and-forget." That mutation has a documented, still-open bug (ISSUES_AND_FIXES.md #29): a failed save leaves the wrong status/rate/score on screen with no rollback. Layering an unawaited side-effect onto a mutation with no reliable failure path risks drifting the XP ledger out of sync silently. Fix #29 first, or make the XP write part of the same transaction as the attendance update — not a detached fire-and-forget call. Updated 2026-07-28: this now also covers Phase 5's spaced-review note upsert (see Phase 5) — it rides the same mutation and inherits the same risk.
Reuse map & dependencies
  • Ranking-with-ties loop copied from earnings.ts:538–546 for the new "Streak & XP Leaders" dashboard card.
  • <StarRating>'s "small typed lookup keyed 1–5" shape is the template for the 30-entry level array and the badge catalog — static content, not a fetched resource.
  • Hard dependency on Phase 1 for practice-driven XP/streaks/most badges (needs HomeworkLog to exist). Zero dependency for the lesson-attendance XP slice — it hooks into an already-shipped mutation and can ship standalone, first.
  • Open product question: streak semantics during a legitimate absence (school exams, a planned trip) are undefined here. A streak breaking during a week the family gave notice for is exactly the "pressure, not motivation" anti-pattern Principle #3 warns against — ships simple (streaks just break) with the gap flagged, not guessed at.

Token infrastructure, and why it still ships regardless

Keep building the shared hashed-token mechanism on its own timeline, independent of what happened to this phase's scope. Its real justification was never really "for parents" — Phase 1 Slice 1B (student self-serve practice) has a hard structural dependency on the same StudentAccessToken primitive, and it's the better-validated half of this investment given the direct enthusiasm for reminders and leveling.

Honest trade-off, not an unqualified improvement: the original plan put Parent Portal first because a read-only surface is a lower-blast-radius place to retire the app's first unauthenticated endpoint. Required-fix #7 (sensitive-field-exclusion tests, still unresolved — see the review) becomes a hard prerequisite for whichever surface goes first as a result.

No distribution channel exists for the link itself yet (no email/SMS infra) — manual copy-paste for the foreseeable future, fine for a handful of families, a real chore past ~15–20. No active leak-detection beyond passive lastUsedAt — reasonable given a leaked link's worst case is bounded to one student's non-sensitive data.

PHASE 4

AI

One bounded structured-generation call for homework drafts, and a firm rule that the model never gets to decide who's at risk — only to describe a decision that deterministic code already made.

Effort: M (5–8 days, not 3–5) 1 new model — AiUsageLog New dependency: @anthropic-ai/sdk

"Generate Homework" — a single call, not an agent

The teacher already has everything the model needs sitting in Postgres — nothing to autonomously fetch or browse. This is squarely a single bounded structured-generation task: claude-sonnet-5 at medium effort, messages.parse() against a Zod schema for guaranteed-valid JSON, matching the app's existing all-Zod convention.

Input:  { studentId, pieceId, lessonId?, teacherHint? }
Context assembled server-side: piece title/description/difficulty,
  last 3 COMPLETE lessons' notes + scores, open spaced-review notes
  for this student — piece-tagged ones filtered to the target piece
  when set, untagged general/technique notes always included, each
  with its checkpoints' recorded outcomes
Output: { bars, handFocus, tempoBpm, dailyGoalMinutes,
          focusNote, difficulty, motivationalNote, dueInDays }

AI drafts, teacher commits — always. The result pre-fills the homework form; it never writes to Homework directly. A hallucinated tempo or an inappropriately hard passage assigned to a beginner is a real pedagogical risk this design treats as non-negotiable to guard against, not a nice-to-have.

Strictly better grounding, added 2026-07-28Phase 5's spaced-repetition redesign turns this from a list of titles into real, teacher-verified pedagogical detail ("Rushes the left-hand entrance in bar 12," with whether the 2-day check went well) — exactly the kind of non-hallucination-prone grounding this section already argued for, and available earlier than before since it no longer waits on Phase 1. See Phase 5.

Pattern detection — deterministic first, language second

All five signals (losing streak, forgetting quickly, improving, at risk of quitting, teacher burnout) are pure functions over already-fetched data, unit-tested like every other src/lib/ module. The LLM's only job — optional, on-demand — is turning a batch of already-computed flags into one warm sentence a busy teacher can skim ("Summarize for me," not auto-run on every load). A rule like daysSinceLastPractice ≥ 3 AND previousStreak ≥ 5 is something a teacher can verify and trust; an LLM classification of the same data is a black box that can flap between visits on identical input. At this scale (tens of students), that trade is not close.

SignalRule
Losing streak≥3 days quiet after a streak ≥5 days higher than current
Forgetting quickly>50% "needed review" outcomes over the last 5 spaced-review checkpoints
ImprovingRolling month-over-month avg score / completion delta, minimum sample both windows
Likely to quit≥2 of 3 signals trending down, AND ≥6 weeks of history (explicit minimum-data gate)
Teacher burnoutNote-completion rate, hours/week trend, cancellation-rate trend — private, supportive framing only

Cost & abuse guard

An immutable AiUsageLog ledger (same ledger discipline as everywhere else in this plan) backs a soft daily cap — 100 homework generations/day, 20 attention summaries/day per teacher. At realistic volume (a few dozen calls a week, single-digit cents each), this is an abuse/blast-radius cap, not real cost control — the actual dollar cost here is negligible and shouldn't be the reason this ships slowly.

Named risks (4)
  • Hallucination is the real liability — mitigated by grounding every prompt in recent lesson notes/scores, never piece-title-alone.
  • Failure modes beyond a missing API key are unspecified — timeout policy, retry policy, and the "generation failed" UX all need to be written down, not implied. Blast radius stays low regardless, since nothing auto-writes.
  • Prompt injection — considered and currently low-risk, since every piece of free text reaching the prompt today is teacher-authored about their own studio. Re-check this the moment any student- or parent-typed free text field is added anywhere in the app.
  • Effort was under-scoped at 3–5 days — real prompt-quality iteration is open-ended; a flat first draft means the teacher never opens the button again. Budget 5–8.
PHASE 5

Analytics, Reminders & Spaced Repetition

The studio-wide view, the nudge that actually arrives on time, and a forgetting curve the app remembers so the teacher doesn't have to.

Effort: M–L (full ~8–10d, MVP ~4–5d) 3 new models 1 new page: /analytics

Spaced repetition — redesigned around her own post-lesson notes Validated 2026-07-28

Redesigned per direct feedback

"I'll have to take notes on what I need to remember after each lesson." The original trigger (Homework.status → COMPLETED, with an auto-derived title snapshot) is replaced by something built around that exact habit: a short teacher-authored note captured the moment a lesson is marked complete — real pedagogical content ("Rushes the left-hand entrance in bar 12"), not a title she already knows. Welcome side effect: this half of Phase 5 no longer depends on Phase 1 shipping at all — it only needs Lesson and Piece, both live today.

The note-capture UI sits in the exact same place Phase 1 adds "+ Assign homework" — AttendanceDialog's COMPLETE-status row, next to the score picker — as a second, independent, collapsed "+ Add a note to remember" link. They're deliberately separate actions, not one merged flow: one is forward-looking (what's next), one is backward-looking (what wobbled today); most lessons will have one but not the other, and keeping both collapsed by default means the fast "tap Present" path that makes this dialog work today is untouched.

model SpacedReviewItem {            // one chain per lesson that got a review note
  lessonId    String @unique     // trigger anchor is Lesson, not Homework
  pieceId     String?            // = lesson.pieceId — nullable; a general/technique note has none, that's fine
  homeworkId  String?            // optional, opportunistic — set only if "+Assign homework" was also used
  note        String             // teacher-authored, REQUIRED, live-editable — the entire point of the redesign
  learnedAt   DateTime           // = lesson.date of the COMPLETE lesson
  checkpoints SpacedReviewCheckpoint[]
}
model SpacedReviewCheckpoint {      // UNCHANGED — child table, not 3 flat columns
  intervalDays Int               // 2, 5, or 10 — exactly per the vision
  dueAt        DateTime
  outcome      ReviewOutcome?    // RECALLED_WELL | NEEDED_REVIEW | SKIPPED
  @@unique([spacedReviewItemId, intervalDays])
}

Trigger, concretely: lesson.markAttendance gains one optional input, reviewNote? (z.string().max(1000), matching the existing note field's own convention). On save, a non-empty note upserts SpacedReviewItem and seeds its three checkpoints via the shared addDaysInTimezone helper; clearing it back to empty deletes the row. Unlike the frozen-snapshot discipline used elsewhere in this plan, note is deliberately live-editable — she should be able to refine what she jotted mid-lesson, the same way the score field already works in this dialog. Until a student-facing surface exists, she marks the outcome from a reminder-feed item — same interaction shape as the score picker, forward-compatible with zero schema change once Phase 1B's token surface ships.

Required fix before implementationThis upsert rides lesson.markAttendance — the same mutation Phase 2's XP hook touches, and the same mutation with a documented, still-open rollback bug (ISSUES_AND_FIXES.md #29, see Phase 2). Fix #29 first, or make this write part of the same transaction as the attendance update — a second silently-driftable side-effect on top of an already-flagged risk is not an improvement. Separately: the onHomeworkCompleted stub hook from the original required-fix list is no longer needed for spaced repetition — only for Phase 2's homework-driven XP — since this trigger moved off Homework.status entirely.

One more consequence worth surfacing to whoever builds Phase 4: its context-assembly already reads "open spaced-review history" as AI prompt grounding — under this redesign that becomes real, teacher-verified pedagogical detail instead of a list of titles, and should be queried by studentId (not only pieceId, since general/technique notes are unattached) so it surfaces for any homework generation for that student.

Reminders — lazy generation, one cron for the clock-sensitive part Validated 2026-07-28

Notifications are recomputed and upserted (idempotent by construction) every time the teacher opens the dashboard — zero new job infrastructure, matching this app's existing effort-realism bar. Named limitation, not glossed over: this cannot deliver the vision's evening nudge ("Your lesson is tomorrow") unless someone happens to open a tab around then. Recommendation: one small Vercel Cron job, nightly, for exactly the clock-sensitive types (spaced-repetition-due, homework-due-soon, lesson-tomorrow) — genuinely small (no new service, no new hosting), and should ship as core Phase 5 scope, not be deferred indefinitely.

Reminder copy is templated strings, not LLM-generated — the vision's own examples ("Only 7 minutes today," "Mochi is waiting") are simple parameterized text; an LLM call would add latency and tone risk for zero benefit here.

Required fix — Postgres NULL uniquenessThe original Notification model made studentId nullable for teacher-level notifications and relied on a compound unique constraint including it for de-dup. Postgres never treats two NULLs as equal, so every teacher-level notification run would insert a fresh row instead of deduplicating — the opposite of "idempotent." Fix: a non-null sentinel value (e.g. studentId: "TEACHER") in the unique key, exactly the pattern Phase 2's StudentBadge.periodKey already uses for the identical problem.

THE CODE REVIEW

Architecture & feasibility review

Five designs were produced in parallel, each grounded independently against the live code. That's deliberate — independent design surfaces more real patterns than one linear pass would. It also predictably produces seam conflicts where two designs solve the same problem differently. This is the review that found them, standing in for a code review since nothing has been built yet.

▲

Not buildable as five parallel drafts. Buildable once reconciled.

Every individual design reuses this codebase's real patterns correctly and invents nothing gratuitous. But two designs define the same StudentAccessToken table with incompatible security postures, and two independently invent an identical Competition model — implemented literally as written, either produces a broken schema push or a silently duplicated feature. Both are reconciled throughout this document (see the "Reconciled" notes above). What follows is the fuller list.

Required fixes before implementation starts

  1. 1
    Unify StudentAccessToken — one hashed schema, one kind enum, one header. Adopted throughout this doc. resolved above
  2. 2
    Unify Competition/StudentCompetition — one model, owned by Student Profile. resolved above
  3. 3
    Designate students/[id]/page.tsx as the single per-student hub — Homework, Motivation, Competitions land as tabs there, not three more routes. resolved above
  4. 4

  5. 5

  6. 6
    Wire Phase 1's integration-hook stubs from day one (onHomeworkCompleted for Phase 2's XP, onPracticeLogged) — cheapest possible insurance against a permanently-empty downstream feature.   7. 7
    Add an explicit sensitive-field-exclusion test for every non-teacher-facing router. This app's 42-test suite covers pure src/lib/ math only — zero router/integration tests exist today, and none of the five designs proposed adding any for the one genuinely new privacy-sensitive surface this plan introduces. A regression here doesn't produce a wrong number, it leaks one family's private data to another. Updated 2026-07-28: since Phase 1 Slice 1B now builds before the re-scoped Parent Portal (see Build sequence), this is a hard prerequisite for Slice 1B specifically, not a general nice-to-have. not yet resolved — see below
Security posture — minimum viable, not gold-plated

Zero rate limiting exists anywhere in the app today, and the only precedent for unauthenticated access (demo.ts) is itself flagged as unguarded (ISSUES_AND_FIXES.md #19). Phase 1B and Phase 3 add the app's second and third public-facing surfaces, ever — in that order as of the 2026-07-28 revision (Slice 1B now builds first, against the fresh token mechanism — a deliberate trade of blast-radius-first for validated-value-first, see Phase 3), where the original plan had it reversed.

Ship these (cheap, and mostly already specified above): hashed tokens at rest · field-level select allow-listing, never include-then-strip · zero mutations on the parent router · revocation + lastUsedAt surfaced to the teacher · a trivial in-memory sliding-window throttle on the token-resolution middleware (the one guardrail neither original design fully committed to — closes a volumetric-abuse gap for about twenty lines).

Skip as genuine gold-plating for a single-teacher, dozens-of-families app: distributed rate-limiting infra, IP-anomaly alerting, CAPTCHA, mandatory token expiry.

Other conventions worth naming once, for every future PR
  • Teacher.timezone is a live, populated, unused trap field — a separate column from User.timezone that every existing router correctly ignores in favor of ctx.session.user.timezone / teacher.user.timezone. Only one of the five phase designs called this out explicitly; worth a standing style-guide note so nobody reaches for the obvious-looking wrong field.
  • "Did this student practice today" is implicitly a multi-row aggregate (a student can have 2+ active homeworks logged the same day) — groupBy/EXISTS, never a naive findFirst.
  • Every model in this plan ships via prisma db push — never migrate dev/deploy — with the dev server stopped before prisma generate, using the local prisma.cmd binary, per this repo's standing rule.
